## R7-A02 第 6 点：文档工作模式 + 能力声明真实性校验（Task #66）

承接上一批（版本化 IPC + 心跳/trace），关闭审计点名的原话：

> "现有 worker 存在且 spawn，但默认导航仍同步，worker handle 主要
> 返回 URL/版本状态；**不能据名称宣称已多核渲染**。"

### 核心判据（本模块的立论）
不是"有没有 worker / spawn 这些**名词**"，而是**文档工作（解析 /
样式 / 布局 / 绘制）在哪执行**：
- 默认导航 `gui._commit_navigation` 仍**同步**调 `page.load_url()`
  → 活在主线程。
- 既有 `DocumentProcessWorker` 处理的是**紧凑身份计数**
  （doc_id/nav_epoch/frame_id/navigation_id），**不**执行真实解析/
  样式/布局/绘制 → 即使真实 spawn，也只是"管道通了"，**不是**
  多核渲染。

### 新增 `toy_browser/app/doc_process_mode.py`（纯逻辑）
- `DocWorkMode` 三态 + `_MODE_CAPABILITIES` 能力表：
  * `MODE_SINGLE_DEBUG`（默认，活在主线程同步）
  * `MODE_WORKER_IPC`（子进程 spawn 且 IPC 通，但 worker 只做紧凑
    IPC/身份计数）
  * `MODE_WORKER_FULL`（worker 持 DocumentSession 执行真实文档工作，
    **当前未接通**）
  * 能力键：`multi_core_rendering` / `worker_isolation` /
    `ui_nonblocking_navigation` / `frame_ipc`。
    **只有 WORKER_FULL 的 multi_core_rendering = True**。
- `detect_doc_work_mode(navigation_is_sync, worker_does_doc_work,
  worker_spawned)`：按**真实接线**探测（不靠名字猜）。
  `worker_does_doc_work` 真 → FULL；否则 `worker_spawned` 真 →
  IPC；否则 SINGLE_DEBUG。默认调用返回 **SINGLE_DEBUG**（如实）。
- `CapabilityClaim(name, capability, mode)` + `is_truthful()` /
  `untruthful_reason()`：用**能力表**校验（非比档位）。越级声明
  （WORKER_IPC 下宣称"已多核渲染"）判 False 并给原因。
  `claim_multi_core_rendering(mode)` 是审计点名场景的便捷入口。
  保守：未知能力 / 未知模式均按**不真实**处理。
- `SingleProcessDebugMode`：**显式**单进程调试模式（审计"保留"）。
  与隐式回退区分：`enable(reason)` 主动 opt-in vs
  `mark_auto_fallback(reason)` 被动；`effective_mode(detected)`
  显式开启时**强制** SINGLE_DEBUG（即使探测到 worker_full），
  保证调试态下活一定在主线程可单步。

### 提交 1 `7a68b83` — 纯逻辑决策层
新增 `toy_browser/scripting/script_trust.py`：
- `classify_url(url, creator_trust)` 四档信任类。**local** =
  file:/about: 等无网络来源 + W3C Secure Contexts 认定的
  potentially-trustworthy **回环源**（localhost / 127.0.0.1 / ::1）；
  **remote** = 其它 http/https/ws/ftp；**opaque** = data:/blob:
  （自身不携带可信性，须**继承创建者** trust，未知按最保守的远程）；
  **unknown** = 空 / 无法解析，保守按远程（"判不出来"≠"可信"）。
- `ScriptTrustGate` 三态策略 `disable_all` / **`local_only`（默认）**
  / `allow_all`；按**源**（scheme://host[:port]，非整条 URL）显式
  `allow_origin(origin, reason)` / `revoke_origin`；策略切换与授权
  均带 reason 入**有界**审计轨迹（256），非法策略名被拒。
- 第 5 点 `ScriptIsolation`：ISO_NONE（脚本与 UI 同进程同线程，
  当前事实）/ ISO_WORKER_IPC（worker spawn + IPC 通，但脚本仍在
  主线程）/ ISO_OS_SANDBOX（OS 沙箱经验证，未实现）。
  **`is_security_boundary` 只由 `os_sandbox_verified` 决定**——
  spawn 了、IPC 通了都不构成安全边界。
  `ScriptIsolationClaim.is_truthful()`：worker_ipc 下"脚本已沙箱
  隔离"判不真实并给原因；未知能力 / 空事实保守按不真实。
- 约定：回环判为 local **不是绕过**——规范把回环当可信上下文，
  与"任意网络页面"是两类东西；这同时保住了既有回环测试服务器
  主链（B05 pending nav 测试就用 127.0.0.1）。

## R7-S02：统一 RequestContext + 无条件策略构建（2 提交）

### 提交 1 `5d62a1f` — 纯逻辑层
新增 `toy_browser/network/request_context.py`（不发请求、不读时钟，
时钟由调用点注入）：
- `RequestContext` 全字段（方案第 1 点逐项）。**`with_base()` 只改
  base_url，绝不给 document_origin 赋值**；`base_rewrites_origin`
  把"<base> 指向异源"暴露为可观测差异。跨源判定含端口；空源按
  最保守的跨源处理。
- destination 八类 + mode/credentials 常量；`default_mode_for`
  （classic 无 crossorigin → no-cors；module / crossorigin → cors；
  fetch/XHR → cors；未知 → None 供调用点明确拒绝）。
- `evaluate_request()` 发送前判定：destination → mode → scheme →
  deadline → 混合内容 → CSP → CORS 顺序拒绝。https 文档里的 http
  **active** 资源（script/style/fetch/xhr/font）阻断，image 属
  optionally-blockable 只标记 `mixed_content`。同源**无需** ACAO；
  跨源 no-cors → opaque；cors → `requires_acao` + 预检标记。
  **不支持的模式明确拒绝**（原因含 `not silently downgraded`）。
- `for_redirect()`：逐跳追加 chain；跨源跳转凭据降级 omit + 剥离
  Authorization/Cookie（fetch §4.6）。
- `filter_response_headers()`：opaque 响应**无任何**可读头；cors
  过滤 forbidden response-header names。

## R7-S02 第 3/5 点：RequestContext 在真实发包路径的消费（020b72c）

### 立论（先探查再动手）
S02 首批（5d62a1f + 接线）已落纯逻辑决策层 `request_context.py`
（`RequestContext` / `evaluate_request` / `for_redirect` /
`filter_response_headers` / `context_for_destination`）+ 第 2 点
无条件策略构建。但**逐入口消费**尚未接进真实发包路径：
- `net.HttpClient.get` / `post` 只消费 `cookie_context`（cookie 门禁），
  不消费 `RequestContext`；
- `_follow_redirects` 只有 `cookie_context.for_redirect`（cookie 降级），
  没有 `request_context.for_redirect`（敏感头剥离）；
- `fetch_resource` / `load_subresources` 逐 spec 派生 cookie 上下文，
  但没有 destination / mode / credentials 维度的发送前评估。

### 改动（决策层已就位，逐入口消费，不重复造轮子）
- **`net.py`** 模块级 `import request_context as _rc`（纯逻辑层，
  无环）；`HttpClient` 新增：
  * `_admit_request_context(ctx, now)` → `_rc.evaluate_request`（纯
    判定，不发包）；
  * `_strip_cross_origin_headers(headers, doc_origin, target)`（跨源
    剥 fetch §4.6 敏感头：Authorization / Cookie / WWW-Authenticate …，
    不修改入参；同源保守不剥，交给调用方 / cookie 门禁决定）。
  * `get(url, ..., request_context=ctx, now=...)`：发送前
    `_admit_request_context`；被拒 → 落地 `HttpResponse(status=0,
    denied=decision, denied_headers=stripped)`，**不发包**；允许 →
    跨源剥头再走缓存 + 重定向链；透传 ctx 给 `_follow_redirects`。
  * `_follow_redirects(..., request_context, now)`：每跳
    `cur_rc.for_redirect(nxt)` 重新评估（跨源降级 omit + 剥敏感头
    + 逐跳追加 redirect_chain）；被拒的那一跳直接落地 denied 占位
    响应（`redirected=True`），不继续发包；允许则跨源剥头后继续。
    第 0 跳不做（已由调用方 `get()` 入口判过）。
  * `HttpResponse` 增可选 `denied` / `denied_headers` 字段（默认
    None，legacy 调用方不变）。
- **`_build_subresource_request_context(spec, absu, doc_origin,
  policy)`**（net.py 模块级 helper）：每个 spec 派生自己的
  destination / mode / credentials（`script` 按 `type=module` /
  `crossorigin` 细分 classic-script / module；image / stylesheet →
  no-cors；fetch / xhr → cors；未知 destination 保持空串供
  evaluate 时明确拒绝，不静默降级）。
- **`fetch_resource(url, ..., request_context, now)`**：透传
  `request_context` 给 `c.get()`；被拒（`resp.denied is not None`）
  按子资源失败契约返回 `None`（与 404 同形）。
- **`load_subresources` / `load_subresources_parallel`**：每个 spec
  派生 `_rc_ctx = _build_subresource_request_context(...)`，传给
  `fetch_resource`；`_apply_policy` 后的 post-fetch 复核保持不变
  （防御纵深：发前拒 + 响应到达后复核）。
- **`browser.py`**：文档主链 `req_ctx`（navigate 模式）保留挂
  `host.request_context`（供 inline 脚本 / 事件处理器里的
  `fetch()` 复用）；子资源加载路径由 `load_subresources` 内部按
  spec 派生各自的 destination / mode（不依赖 navigate 模式 context
  做子资源请求——那会误把 navigate 的 `same-origin` 凭据默认强加

POST 路径的 CORS 校验也未接（本批只接 GET/HEAD）。这两块都是
真实网络行为，留活显示批次。

## R7-S02 第 5 点真实 OPTIONS 预检往返（本批落地，提交待定）

上文"CORS 响应校验纯逻辑层"之后，本批把**真实 OPTIONS 预检请求的
发送**做落地了（不再是"标记需要预检 + 校验响应头"的纯逻辑，而是
真实先发 OPTIONS 网络往返）。POST 路径的 CORS 校验也一并接上。

### 改动
- **`net.py` — `HttpClient` 新增 OPTIONS 预检路径**：
  * `__init__` 加 `self._preflight_cache: dict = {}`（跨源 CORS 预检
    结果缓存，per-client 生命周期，不读时钟；键 = 目标源+方法+
    自定义头指纹，值 = PreflightCheckResult，只记"通过/不通过 +
    可见头"，不存响应头，不冒充服务端行为）。
  * 新增 `_preflight_cache_key(target_url, method, custom_headers)`：
    静态方法，对 (目标源, 方法小写, 自定义头稳定指纹) 生成缓存键；
    指纹用自定义头 (小写名, 值) 排序后的 md5 前 16 位（保留头
    Access-Control-* / Origin / Host / UA / Accept 不计入指纹）。
  * 新增 `_issue_preflight(target_url, method, headers, doc_origin,
    credentials_mode)`：对跨源目标发一次**真实** OPTIONS 预检。
    复用现有 `_acquire_conn` / `_release_conn` / 重试循环 /
    `_admit_request` 门禁；预检缓存命中直接返回；未命中则
    `conn.request("OPTIONS", path, headers=preflight_hdrs)`（带
    Access-Control-Request-Method / Access-Control-Request-Headers /
    Origin），响应到达后经 `_rc.validate_preflight_response` 比对
    ACAO/ACAC/Expose-Headers；连接失败/取消 → 按"预检不通过"处理
    （降级 opaque，不抛异常——预检失败在规范里就是"响应不可读"，
    不是硬错误）。
  * `get()` / `post()` 在**真实请求发出前**做预检：
    `requires_preflight`（跨源非简单请求 / credentials=include /
    带自定义头）→ 先 `_issue_preflight`；**预检不通过 → 真实请求
    不发出**（符合真实浏览器行为：预检失败时请求不发出，JS 侧看到
    TypeError 网络错误），直接返回占位响应（status=0 +
    `cors_resolved_type=opaque` + `cors_allowed=False`，denied 仍为
    None——请求本身合法，只是预检未过）；预检通过 → 真实请求发出，
    响应挂 `cors_check` / `cors_resolved_type` / `cors_allowed`。
    同源 / 跨源简单请求（无自定义头）无需预检，响应到达后经
    `validate_preflight_response` 比对 ACAO/ACAC（原有纯逻辑路径不变）。
  * `HttpResponse` 加 `cors_check` / `cors_resolved_type` /
    `cors_allowed` 三字段（默认 None/""/True，同源 / 无 CORS 判定
    的正常路径不填）。
  * `FetchTransport._cors_request_context` 把真实请求的 method 与
    自定义头带进 RequestContext（`ctx.method` / `ctx.headers`），
    让跨源 POST + 自定义头正确标记 `requires_preflight=True`。
  * `FetchTransport.fetch` 的 POST 路径也传 `request_context`
    （本批接上 POST CORS 校验）。
- **`js.py`** 让 JS 侧消费真实校验结果：
  * `_fetch_response` 加 `cors_check` 参数；提供时 `type` 直接取
    校验后的 `resolved_type`（ACAO 不匹配降级 opaque / 校验通过
    保持 cors），`headers` 用校验结果的 `visible_headers`（∪
    Expose-Headers 允许头），不再走 `_js_filter_response_headers`
    的默认过滤（避免与校验层各写一套）。
  * `_fetch` 调用处把 `resp.cors_check` 传进 `_fetch_response`。
  * XHR `send` 路径：`resp.cors_check` 提供时优先用校验结果的
    `visible_headers`（不通过时为空，降级 opaque，XHR 读不到任何
    响应头），否则走原有 `_js_filter_response_headers`。
- **`tests`**：
  * `test_r7_s02_s03_policy_cookies.py` 新增 3 项 OPTIONS 预检集成
    测试 + `_start_server` 加 `do_OPTIONS`：
    - `test_s02_preflight_options_roundtrip_cross_origin_post`：
      跨源 POST + 自定义头 → OPTIONS 预检被真实发出（counts 验证）
      → 通过（ACAO:*）→ 真实 POST 发出 → cors。
    - `test_s02_preflight_options_roundtrip_fails_on_mismatch`：
      跨源 OPTIONS 预检**不回** ACAO → 预检失败 → 真实 POST
      **不发出**（counts POST==0）→ 占位响应（status=0、
      opaque、denied=None）。
    - `test_s02_preflight_cache_key_stable`：预检缓存键对
      (源, 方法, 自定义头指纹) 稳定，不同方法/不同头各自独立。
  * `test_r7_j03_fetch_xhr_events.py` 的
    `test_fetch_cross_origin_js_response_type_cors` 修正预期：
    server B 须回 `Access-Control-Allow-Origin: *` 才判 cors
    （原来不回 ACAO 直接判 cors，是"不冒充通过"的缺陷——ACAO
    不匹配应降级 opaque）。

### 坑
- **POST 路径预检失败仍发真实请求（与真实 CORS 规范矛盾）**：
  第一版把预检放在"真实响应到达后"，导致预检失败时真实请求已发出。
  真实浏览器行为是预检失败时**不发**真实请求（JS 侧 TypeError）。
  修复：把预检移到"真实请求发出前"，预检不通过直接返回占位响应。
  同步修正测试断言（POST 计数 0、status=0、denied=None）。
- **ACAO 校验比对目标 origin（之前批次已修，本批无复现）**：
  本批 `validate_preflight_response` 已用 `ctx.document_origin`
  （发起 origin），未复现旧 bug。

## R7-A02 第 2 点：worker 持 DocumentState 执行真实文档工作（提交 89b8969）

### 决策
`DocumentProcessWorker` 从"只回紧凑身份计数（doc_id / nav_epoch /
frame_id / navigation_id）"升级为"按 tab 持有 DocumentState（DOM /
Host / 资源 / 版本长期留 worker 进程，G07 step 4"DOM 长期留该
进程"）并执行真实文档工作"。复用既有 `render_document_state`
（解析 + JS + 样式 + 布局 + 光栅化）与 `render_document_state_restate`
（重排，不重建 Host、不重跑脚本），不重复造轮子。

### 接线
- `DocumentProcessWorker.__init__` 加 `_doc_states` / `_last_bitmap` /
  `_has_done_doc_work` 三字段。
- 新增 `_do_doc_work(tab, cmd, payload)`：navigate 带 html →
  `render_document_state`；resize/scroll（tab 已有 DocumentState）→
  `render_document_state_restate`（script_init_count 保持 1，不重跑
  脚本）。
- 新增 `doc_state_for(tab)` / `last_bitmap(tab)` /
  `has_done_doc_work()` 访问器；`drop_tab` 清理 `_doc_states` /
  `_last_bitmap`。
- **关键修正（避免 navigate 早期 return 吞掉文档工作）**：原
  `handle` 的 navigate 路径在 276 行早期 return，`_do_doc_work` 永远
  到不了 → 把 navigate 的 html 路径 `_do_doc_work` 调用移到 return
  之前；resize/scroll 路径（tab 已有 DocumentState）在 STOP 判定
  前调用。帧 payload 只带白名单键（kind/url/frame_id/doc_id/
  navigation_id），**不**带 w/h（`FramePayloadContract._WHITELIST_KEYS`
  不含 w/h，带了会被父进程可见面校验拒收）——几何由父进程侧经
  `frame_spec_for(命令 payload)` 取，与既有 resize/scroll 帧同口径。
- `DocProcessServer.has_done_doc_work()` 代理**父进程内置同步
  worker** 的标记（回退态可观测）。**不冒充通过保守口径**：子进程
  存活（多核态）时父进程无法直接观测子进程是否做了真实文档工作，
  代理保持 False（不代子进程返回 True）——多核 WORKER_FULL 需子进程
  经 IPC 回报 doc_work 标记（开放问题，留活显示批次：IPC 协议扩展
  + 活显示实测）。
- `gui._r7_a02_doc_mode` 的 `worker_does_doc_work` 从写死 `False`
  接到 `self._g07_doc_server.has_done_doc_work()`——`detect_doc_work_mode`
  据此可在 worker 真做了文档工作时判 WORKER_FULL（而非永判
  WORKER_IPC）。
