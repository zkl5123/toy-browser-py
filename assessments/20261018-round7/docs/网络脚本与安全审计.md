## 3. P0：不可信内容上线阻断项

### S01 Python 宿主对象越界可达（实测暴露，严重利用未验证）

探针 `host_private_attributes` 在页面 JS 中得到：

- `location._host.doc_url` → 合成文档 URL；
- `localStorage.__class__.__name__` → `Storage`；
- `fetch.__self__._js_step_budget` → `20000`。

调用链：`web_api.ToyLocation._host`（`scripting/web_api.py:368-375`）/ `Host.globals['fetch']` 绑定方法（`scripting/js.py:4077`）→ `Interpreter.eval_member` → 无白名单 `getattr`（`js.py:3153-3161,3223-3227`）。普通对象赋值还直接 `setattr`（`js.py:3259-3271`），方法调用有原生属性 fallback（`js.py:5795-5799`）。这已经足以证明“JS sandbox”没有可靠对象能力边界。**不声称已获得代码执行、读取文件或成功修改预算**；这些后果未尝试。

修复：
1. `scripting/js.py` 统一 dot/bracket/optional-member/call/write 属性分派，不再对任意 Python 对象执行 getattr/setattr。
2. `web_api.py`、DOM、Response、Promise 用显式可见属性/方法描述表，内部状态留在宿主私有映射；不能只禁止双下划线，因为 `_host` 也已经越界。
3. 页面执行迁移到可终止的隔离进程，限制 IPC 能力、文件/网络访问与总资源；进程隔离不是属性白名单替代品。
4. 完成之前默认禁用不可信远程脚本或明确仅允许可信测试页面。

验收：上述三项返回 undefined/抛标准 TypeError；dot、bracket、方法提取再调用、DOM node/observer/XHR 等全部同样不可越界。只用合成对象元数据回归，禁止以真实秘密验证隔离。

### S02 fetch/XHR 没有 SOP/CORS/connect-src 门禁（回环集成实测）

`cross_origin_fetch_and_samesite`：文档来源 `localhost:<port>`，请求 `127.0.0.1:<port>`（不同 origin/site），服务不返回 ACAO；脚本仍读取 status=200 和 `_text_value=LOCAL_SYNTHETIC_DATA`。`cross_origin_xhr_method` 通过标准 `responseText` 得到相同合成正文。`csp_connect_none` 在文档策略 `connect-src 'none'` 下仍请求 `/connect-none` 并输出 200。

调用链：`Host._fetch`（`js.py:5480-5544`）/ `_Xhr.send`（`js.py:5596-5645`）→ `FetchTransport.fetch`（`network/net.py:1621-1634`）→ `HttpClient.get`。没有请求 origin、credentials mode、DocumentPolicy 或 CORS 校验参数。`is_policy_allowed` 的存在不能代表 fetch 路径已受保护。回环请求未用于论证 mixed-content，因为回环有潜在可信来源例外。

修复：
1. 新建明确 RequestContext 数据模型，由文档传递 origin、site-for-cookies、mode、credentials、destination、method、policy、referrer；不得把 base URL 当成 origin。
2. 在每次发送及每个 redirect hop 前应用 connect-src、scheme 和混合内容政策；响应通过 CORS 后才能构造页面 Response/XHR 可见数据。
3. 发正确 Origin；实现凭据模式和 ACAO/ACAC 联合检查；跨源 include 不接受 `ACAO:*`。实现非简单请求预检，尚未支持的选项应明确拒绝。
4. fetch/XHR、导航和所有子资源共用策略入口，不能只修一个包装函数。

验收：两个回环来源组成同源/跨源、允许/缺失 ACAO、credentials/include、预检、跨源重定向矩阵；拒绝时 fetch 为 TypeError、XHR status=0 且正文不可见；connect-src none 的服务器请求计数为零。

### S04 网络响应限额不是分配前防护（小样本实测，资源耗尽未尝试）

`read_before_cap` 用 129 字节内存回复与 128 字节限额，记录到 `read()` 无参数。实际是**完整读取后**抛 ResponseTooLarge（`net.py:1016-1022`），无法阻止先分配完整内存。gzip 同样 `gzip.decompress` 后检查（`1695-1701`）。

`response_limits_and_cookie_ingest` 在真实回环客户端设 `max_response_bytes=128`：小 gzip 解压成 4096 字节被正常返回；POST 返回 4096 字节也未拒绝。前者是 `_single_get` 调用 `maybe_gunzip` 未传实例上限（`1032-1037`），后者是 POST 无检查（`1195`）。

修复：GET/POST 共用流式有界 reader；预读 Content-Length 但不信任它作为唯一校验；逐块累计 raw/decoded 字节并在超限前停止；增量解压且限制输出；超限关闭连接不得入池；传递实例限额；增加请求/页面聚合预算、wall-clock deadline 和取消机制。

验收：128 字节上限遇到 129 字节 raw、gzip 输出及 POST 均拒绝；fake reader 证明每次读参数有界；回环压缩样本最多几 KiB 即可，不需要内存耗尽载荷。真实超大体积/解压炸弹未运行，不能宣称已经测试抗资源耗尽。

## 4. P1：安全会话与真实页面功能差距

### S05 Cookie 作用域与请求上下文

回环实测：`cross_origin_fetch_and_samesite` 的请求含 `strict_marker=synthetic`，且 Origin 缺失。`_single_get` 虽支持 `cookie_context`（`net.py:915,965-972`），public `get` 和 `_follow_redirects` 没有传递（`1061-1064,1723-1727`），实际走默认同站顶层 GET。

内存实测 `cookie_scope_validation`：
- 无 Domain 的 host-only cookie 被发送到子域；Cookie 没有 host_only 字段（`cookie_store.py:41-44,126,288`）。
- `Domain=test` 可影响 `.test` 下另一个兄弟域；仅后缀匹配，无 PSL（`170,78-92`）。
- 非法 SameSite 值被保存，跨站 POST 仍发送，默认防护失效（`159-160,299-305`）。
- `for_url('/public')` 返回 `Path=/private` cookie；该方法未检查 Path（`310-346`）。
- 非回环 HTTP 可设置 `__Secure-a=1; Secure`；未拒绝不安全来源设置 Secure，前缀约束未实现。

回环还证明多行 Set-Cookie 仅保留最后一个，POST 的 cookie 未入库：最终 cookie_names 只有 `second`。原因 GET headers dict 推导覆盖（`net.py:1023-1025`），POST 无 ingest（`1195-1207`）。

修复：Cookie 持有 host_only/creation_time，维护 PSL 域验证及前缀规则，缺失 Path 使用请求目录默认值，非法 SameSite 归默认；所有查询共用同一匹配器；多值响应头结构保留 Set-Cookie 每条；所有响应包括 redirect/POST 统一入库；请求上下文来自 S02 的 RequestContext；站点计算基于 scheme + registrable domain 而非简单 host 不同。

验收：host-only 不传子域、Domain cookie 正确传子域、公共后缀拒绝、Path 正反例、Secure/前缀约束、过期/Max-Age 优先级、重复 Set-Cookie、跨站导航/子资源/POST/redirect 矩阵。Cookie 数量/单条字节/总量也应有配额与驱逐。

**HttpOnly 定性**：有字段不等于完成文档 cookie API；当前 `_document_obj`/`eval_doc_method` 未接入 cookie getter/setter（`js.py:4151-4172,5658`）。本次没有把“普通 document.cookie 可读 HttpOnly”当作实测缺陷。宿主暴露另属 S01，不应与 API 支持混淆。

### S06 CORS 模式误判，正常脚本也被阻断

`csp_self_same_origin_script`：同源 `/a.js`、`script-src 'self'`、没有 ACAO，被丢弃。`net.py:2013-2014` 在有 doc_csp 分支对所有脚本检查 ACAO，未先判断是否跨源，并行 `2125-2126` 相同。

`classic_cross_origin_script`：无 crossorigin 的 classic script 被强制按 cors 模式，缺 ACAO 即拒绝（`net.py:1984-1988,419-429`）。标准 classic script 默认 no-cors，module/crossorigin 场景才需相应 CORS；不能把执行第三方 classic 脚本与 fetch 读取混为一谈。

修复：`collect_subresources` 保留 type/crossorigin/integrity/referrerpolicy 和 destination/mode；同源不要求 ACAO；classic/module/credential 模式分别实现。验收覆盖同源 CSP self、跨源 classic 无 ACAO、module 无 ACAO 拒绝、crossorigin anonymous/use-credentials 及正确凭据策略。

### S07 Response Promise、XHR 请求方法与事件契约

实测 `cross_origin_fetch_and_samesite` 的 `r.text()` 进入 catch，错误值为 `LOCAL_SYNTHETIC_DATA`。根因 `_fetch_response` 使用 `lambda rj, rs: rs(body_text)`（`js.py:5423-5424`），而 `_make_promise` 的 executor 参数顺序是 `executor(_resolve, _reject)`（`5380`）；json/arrayBuffer 同样写反（`5431-5436`）。此外 json 解析异常被变成 None（`5426-5430`），不是拒绝。

`cross_origin_xhr_method` 发 `open('POST',...)`+`send('synthetic')`，回环服务实际收到 GET；`_method` 仅储存不使用（`5591-5594`），`send` 总调用 GET transport（`5620`）。XHR HTTP 非 2xx 被 onerror（`5631-5634`），真实 XHR HTTP 错误仍属于成功完成传输，应 onload。fetch 当前对 4xx 保留 Response 的行为（`5527-5535`）反而正确，不能按过时 docstring 认定它拒绝 HTTP 错误。

修复：纠正 executor 顺序/Response Body 方法错误路径，移除私有明文兼容字段；请求 transport 支持 method/body/headers；按网络失败与 HTTP status 分开事件；补 statusText、headers、重定向最终 URL、bodyUsed 和单次消费。验收：text/json/arrayBuffer 成功兑现，非法 JSON 拒绝 SyntaxError；fetch 404 fulfilled(ok=false)，XHR 404 onload，网络失败 reject/onerror；POST 方法与 body 原样到达回环服务。

### S08 Event loop 和脚本生命周期

`event_loop_order` 实测 `sync → next-script → timer → micro`。核心 `execute_scripts_in_order` 遍历完所有元素后才 `flush_timers/flush_microtasks/flush_raf`（`js.py:6831,6923-6925`），`flush_timers` 最后才微任务（`7141-7169`）。正常语义至少要求当前任务结束后微任务先于下一 timer；解析器脚本间还应建立适当微任务检查点。代码中“V8 sync→timers→microtasks”的注释是错误标准描述，不可据此修改预期。

静态：先 `dom.parse(html)` 再运行所有脚本（`browser.py:116,187`），不存在 parser-blocking 可见 DOM 阶段；脚本集合一次抓取（`js.py:6822-6829`），async/defer/module 未分队列。`_script_is_js` 对少数 data type 以外的 type 全部返回 True（`6760-6767`），也不是 HTML 脚本类型算法。未找到完整 document.readyState/DOMContentLoaded/load 生命周期实现。

修复：独立页面调度器，建立任务→微任务检查点→渲染机会；定时器以单调时间 deadline 运行而非“渲染前清空”；微任务每次任务后 drain；解析器脚本/defer/module/async 分别编排；导航时取消旧 document generation 的任务。验收：脚本间 Promise、两个 timer 间微任务、嵌套 timer、rAF 及 DOMContentLoaded/load 次序；新文档不得执行旧文档回调。测试保持有界，不构造无限微任务风暴。

### S09 Web Storage 配额与生命周期

`storage_lifecycle_and_quota`：把限额在内存临时降到 16 字节后，setItem 超额正确抛 QuotaExceededError；但同源新 Host 得不到前一 Host 的值。`register_web_api` 每次 `Storage()`（`web_api.py:485-486`），没有 origin 键空间或 tab session 生命周期。**不是已证明跨源共享泄漏**，而是过度隔离/无法持久保留，以及没有完整安全存储模型。`Storage._store` 暴露问题由 S01 统一解决；本次只验证私有元数据读取，没有执行额度绕过写入。

修复：宿主侧 StorageService，以规范化 origin/opaque origin 分区；localStorage 按 profile origin、sessionStorage 按 top-level browsing context+origin；总配额与单 origin 配额；增量计算大小，拒绝前检查，失败原子化；DOMException 映射及 storage event。验收同源导航保留、不同端口/协议隔离、tab session 隔离、opaque origin 拒绝、覆盖写额度扣减正确、直接属性和 setItem 契约一致、超额不能改动旧值。

尚存静态差距：每次递归重新建立 seen 集合（`196`），不是整条脚本导航链的去重；递归使用原 `client=client` 而非实际 `eff_client`（`213`），默认创建的会话/连接不能按预期延续；只消费第一个合适请求，replace/history 和 same-document 生命周期不完整。具体 GUI 行为由集成审计负责，此处不声称已完成 GUI 导航实测。

**GUI 接入静态复核**：`app/gui.py:748-772` 独立创建 Host、执行脚本后，直接 `load_html(..., run_scripts=False)` 和记历史（`785-786`），随后返回（`803`）；整个 gui.py 未发现 `_pending_nav` 的读取。因此 B05 当前只证明脚本 API 排队和 browser.py 渲染 API 跟随，**GUI HTTP 首次加载管线未消费导航任务**，不能把前者等同 GUI 实际跳转。本轮没有操作真实 Tk 窗口，定性为静态确认的接入缺口。

**GUI 刷新/历史策略分歧（与 integration-audit 交叉确认）**：首次 `load_url` 从响应建立 DocumentPolicy（`gui.py:727-772`）；后退/前进（`822-832`）和 `reload`（`968-970`）调用 `_load_no_history`，HTTP 分支仅 `fetch_html` 然后 `load_html`（`858-859`），丢弃响应策略头。`load_html` 默认 `run_scripts=True`（`161-164`）并无参执行 `_host.execute_all()`（`254-257`），没有 CSP 参数。因此代码路径可确认刷新/历史加载丢失 CSP，且子资源/FetchTransport 也没有复用首次加载配置；这是静态调用链证据，不混入 21 项探针实测计数。应作为 S03 的额外入口缺口处理。

修复和验收：NavigationController 持有跨跳 seen、稳定 session/client、history 更新及 generation 取消；GUI/CLI 及刷新/历史必须共用同一文档加载入口。验证 A→B→A 有界拒绝、replace 不增加历史项、assign 增加历史项、hash 不重新获取文档、旧 timers 不跨页继续；同一 CSP fixture 在 GUI 首次/刷新/前进/后退均阻止内联脚本。需要区分导航排队成功与完整浏览器历史语义通过。

## 6. 静态风险与未验证列表

1. **重定向敏感头**：`_follow_redirects` 每跳复用 headers（`net.py:1723-1727`），没有跨源 Authorization/Cookie 剥离；本次未向任何真实服务发送敏感头。
2. **缓存语义**：`_CacheEntry.ttl` 先 max_age 再 no_cache（`net.py:1256-1261`），混合指令可能不重验证；304 返回仅当次 headers 并声称会合并却未实现（`999-1014`）。Vary、凭据缓存键与 304 策略头保留需要专门回环回归，不作本次实测结论。
3. **连接清理**：dead 分支 `_release_conn` 直接 return 不显式 close（`891-892`），错误重试未统一 finally；资源生命周期风险未做压力测试。
4. **混合内容/opaque origin/跨文档隔离**：没有看到与统一 RequestContext 对应的完整政策；未做公网 HTTPS 或 iframe/window 真实浏览器差分。
5. **全局资源预算**：现有 JS 步数不代表内存/CPU wall time 限额；cookie、WebSocket._sent、队列/DOM/脚本源码数量缺少统一 aggregate cap。未进行大规模分配或阻塞攻击。
6. **CSP 完整语义**：host/scheme 通配、nonce/hash、重复响应头、meta、sandbox/frame-ancestors、report-only 等不是本次通过项目；不能用自有 unit test 通过推断兼容 CSP3。
7. **真实标准对照范围**：本次依据浏览器平台基本语义审查，不启动外部真实浏览器，也不读取旧差分输出作为本次实测。涉及 GUI 交互与渲染的独立报告可补交叉证据。
