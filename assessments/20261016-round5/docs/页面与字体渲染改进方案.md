# 页面与字体渲染改进方案

日期：2026-10-16。本文补充第五轮评估，聚焦“字体不好看、文字挤压、页面读起来不像真实浏览器”的问题。依据包括现有页面截图、百度诊断错误页、字体源码核查，以及本次新增的字样渲染样本。本文是改进建议，未修改产品渲染实现。

**优先结论：当前首先需要修复字形正确性，其次统一文字测量、行布局和绘制，再改善小字号抗锯齿及 DPI。仅换成微软雅黑、提高采样数或改用 GPU，都无法修复错误轮廓、丢失的字形偏移和不一致的基线。**

## 1. 现状证据：字体已经发生形变

使用仓库现有 `fonts/arial.ttf`，在独立探针进程中将同一字体注册为测试用字体，直接调用项目 `text.draw_text` 生成 12、16、24、36、48px 样本。这样绕开网页布局、网络和中文回退，单独检查当前字形绘制。

![当前引擎绘制自带 Arial，圆弧、字腔和字距存在异常](../font-rendering/current-glyphs.png)

可见 `O/Q` 圆弧断口、`B/8` 字腔畸变、`g/@/%` 等复杂轮廓失真；在大字号下仍明显，不能仅归为小字号不够清晰。小字号还出现拥挤和笔画不均。

本图不是改进效果图，也不是与浏览器逐像素比较的结果。字体哈希、轮廓和掩码字段检查见 [observations.json](../font-rendering/observations.json)，复现脚本见 [specimen.py](../font-rendering/specimen.py)。原第五轮中文和表单截图仍用于整页问题追溯。

## 2. 已核实的问题及其表现

| 问题 | 源码依据 | 对画面的影响 |
|---|---|---|
| 轮廓边界丢失 | `ttf_font.py` 解码时读取 endPtsOfContours，但简单轮廓返回扁平点列表；`GlyphOutline` 无轮廓边界字段 | 多个轮廓可能被当作一个多边形连接，字腔、断开的部件及复合字形容易错误 |
| 二次曲线没有正确进入绘制路径 | `rasterize.py` 有 `_flatten_quadratic`，但 `_contour_to_points` 没有调用它；其处理离曲线点时主要取中点组成折线 | 圆弧和转角不能忠实表达原字形；加大字号仍会失真 |
| 字形定位信息丢失 | `rasterize_glyph_mask` 计算 x0/y0 后将图形移至掩码原点；`GlyphMask` 仅有宽高和覆盖数据，blit 以 pen_x、baseline-mask.h 定位 | 左侧承、字顶和下降部定位不正确；`g/j/p/q` 等可能看起来漂移或挤压 |
| 字符位置提前取整 | `draw_text` 多处 `int(cx)`、`int(cy)`；掩码不包含亚像素相位 | 相邻字距跳动，缩放时文字抖动，细笔画粗细不均 |
| 测量与绘制并未共用最终 glyph run | 测量缓存以字符/字号为主，绘制另行解析字体、字重、字距并再次 wrap | 换行、对齐和实际墨迹位置可能不同；不能只修绘制不修布局 |
| 混合字体按各自上升部偏移 | `draw_text` 针对回退字体使用各自 ascent 计算基线偏移 | 中英文混排的共同基线、上下留白与行高需要统一，不能逐字按行顶重新确定基线 |
| 字体回退过于粗略 | 字体初始化主要注册 serif/monospace；最终回退允许任意可用 TTF；缺字路径存在 `ord(ch) & 0x7F` | CSS 字族选择不可靠，中文、符号可能误替换成无关 ASCII，而不是明确缺字 |
| 抗锯齿采样较粗 | 常见路径为 2×2 覆盖；合成粗体路径还可能关闭抗锯齿 | 小字号曲线、斜线及粗体出现台阶；前提是轮廓本身先正确 |
| 样式与缓存键不足 | 掩码键主要是字符、字体对象 id、半像素字号桶和粗细；未覆盖 DPR、斜体和渲染模式等 | 扩展缩放/样式后可能误复用旧掩码，产生错误尺寸或外观 |
| 页面行内布局近似 | 布局已有基线字段，但部分行内处理仍使用估算基线；绘制阶段还自行 wrap/strip | span/strong/em、空格、链接和文字段落的位置与可读性受影响 |

以上是代码和样本能够支撑的具体问题。完整 hinting、复杂文字 shaping、彩色 emoji 等是需要补齐的能力方向，并非本次已在所有语言上完成的失败实测。

相关实现位于 `toy_browser/typography/`、`toy_browser/layout/layout.py`、`toy_browser/rendering/paint_engine.py` 和 `toy_browser/app/gui.py`，均为项目根目录相对路径。

## 3. 路线选择

| 路线 | 建议用途 | 实施重点与限制 |
|---|---|---|
| A：继续完善纯标准库字体后端 | 保持当前项目定位，近期必须修的基础路径 | 修轮廓、曲线、bearing、行框、灰度覆盖和缓存；完整 TrueType hinting、OpenType shaping 的长期成本很高 |
| B：Windows 可选 DirectWrite 后端 | 当前 Windows 环境追求接近系统文本质量的候选方案 | 通过薄适配层获取字体匹配、字形映射/定位和字形渲染；COM/原生互操作需明确线程与资源生命周期。只接字形/成形层，保留浏览器自己的 CSS 行布局 |
| C：可选 FreeType + HarfBuzz 后端 | 未来跨平台和复杂语言支持 | HarfBuzz 负责 shaping，FreeType 负责字形加载与光栅化；字体回退、行分段、断行和 CSS 排版仍由项目协调，会引入可选依赖 |

建议先完成 A 的几何正确性和公共接口，同时做 B 的小范围验证；若确定跨平台目标，再评估 C。不要同时维护三套段落布局，也不要测量用一套后端、绘制用另一套后端。

Microsoft 文档说明 DirectWrite 提供字体枚举、回退、字形处理及不同层次的布局/渲染接口，并可配合不同图形后端使用。[DirectWrite 官方介绍](https://learn.microsoft.com/en-us/windows/win32/directwrite/introducing-directwrite)

FreeType 教程明确区分 advance、bearing 与边界；HarfBuzz 将 Unicode 文本转换为带定位的 glyph 序列，不能替代整套浏览器排版。[FreeType 字形度量教程](https://freetype.org/freetype2/docs/tutorial/step2.html)、[HarfBuzz 官方说明](https://harfbuzz.github.io/what-is-harfbuzz.html)

## 4. 逐项实施步骤

### T01｜P0：保留轮廓边界和完整曲线

**位置**：`typography/ttf_font.py` 的 `GlyphOutline`、简单/复合 glyph 解码；`typography/rasterize.py` 的轮廓展开。此节模块路径均位于 `toy_browser/` 下。

1. 将 Outline 改为 contours 或 points + contour_end_indices，保留每条闭合轮廓；复合字形对子轮廓分别做变换，不能把不同部件首尾直接相连。
2. 按 TrueType on-curve/off-curve 规则恢复直线及二次 Bézier：相邻离曲线点之间补隐含中点，并正确处理轮廓首尾均为离曲线点的情况。
3. 真正调用自适应曲线展开；flatness 用设备像素误差定义，比较控制点到弦的距离，包含弦长归一化与零长度弦处理，避免当前量纲不一致的误差判断。
4. 对多轮廓统一填充，按字体轮廓方向和所选填充规则处理字腔；首先验证非零环绕规则，不能把所有字体轮廓直接拼成一个 polygon。
5. 保留异常字体的点数、递归深度和边界检查；坏轮廓回退到明确缺字标记并记录，不能越界或静默生成任意字符。

**验收**：同一 Arial 的 O/B/8/@ 不再断裂、错误填洞；圆弧随字号平滑放大；含多个组件的字符保留各自轮廓。先过形状，再看抗锯齿。

### T02｜P0：把 bearing、基线与 advance 分开保存

**位置**：`typography/rasterize.py` 的 `GlyphMask`、`rasterize_glyph_mask`、`blit_glyph_mask`；`typography/text.py`。

1. 定义 GlyphBitmap，至少保留 width/height、bitmap_left、bitmap_top、coverage、glyph_id 和渲染尺寸。掩码留白/采样边框必须计入偏移。
2. 在字形局部坐标生成位图，屏幕定位统一使用 `x = pen_x + bitmap_left`、`y = baseline_y - bitmap_top`，按实际位图边界推导，不能用 `baseline-mask.h` 代替 top。
3. pen 只按 glyph advance 前进，不按墨迹宽度前进；负左侧承、右侧 overhang 和下降部允许超出 advance 区间。
4. 布局保留逻辑边界，绘制另存 ink bounds，用于裁剪、脏区和效果扩张；不能为了消除重叠而任意加字距。
5. 增加 j/f/斜体、g/p/q/y、重音、空格和负坐标裁剪测试，比较缓存前后与直接绘制路径的一致性。

**验收**：下降部落在共同基线下方，空格不产生墨迹但仍前进，左右边缘不裁字，缓存命中不改变定位。

### T03｜P0：统一测量、换行、绘制和命中数据

**位置**：`typography/text.py`、`layout/layout.py`、`rendering/paint_engine.py`。建议新增 `typography/runs.py`。

1. 定义 GlyphRun：字体 face 身份、字号、字重/样式、方向、glyph IDs、clusters、advances、offsets、逻辑/墨迹边界和 baseline。
2. 样式解析后分出 font/style/script/direction run；测量使用最终 glyph advances，布局生成 line box 与确定的 glyph positions。
3. Paint 命令引用已布局 run，移除绘制阶段独立 wrap/strip 的职责；white-space 折叠必须在布局规则中完成，pre/pre-wrap 不能靠 strip 实现。
4. 文本测量缓存、字符选择、光标和点击命中共用 cluster 映射与位置；粗体、letter-spacing、word-spacing 必须参与同一过程。
5. 对“普通文字 + strong + em + a + 中文”连续行测试边界、断行、空格和点击；按同一行的最终位置绘制，而不是每个 span 重新起一段。

**验收**：测得的宽度与排出的逻辑宽度一致；窗口宽度变化后绘制不发生第二次不同断行；粗体和行内元素不再脱离文字流。

### T04｜P0：建立真实的字体匹配和有序回退

**位置**：`typography/font.py`、`typography/ttf_font.py`、CSS 字体属性解析；可选后端适配层。

1. 完整解析 `font-family` 列表与引号；建立 family/style/weight/stretch 到 face 的映射，区分 sans-serif、serif、monospace、system-ui，不能全部最终随意选 Arial。
2. 网页显式指定的字体优先；仅对通用字族采用平台默认映射。Windows GUI 可将 system-ui 解析为合适的系统 UI 字族，中文按覆盖能力继续回退，而非全站强制微软雅黑。
3. 依顺序尝试作者字体、指定系统字族、通用字族、语言/符号回退；按字符簇检查覆盖，避免组合字符/emoji 中途拆换字体。
4. 把最终 font face、文件/集合索引、字重和回退原因暴露到开发诊断；未找到时显示明确 .notdef，移除把 Unicode 截成 7bit ASCII 的视觉替代。
5. 字体搜索结果可缓存，但新增字体、加载完成和配置变更后必须有版本失效；不将用户机器某个特定字体的存在作为隐含前提。

**验收**：字体选择可追溯；中文、拉丁、数学符号不会错误显示成别的字符；作者选择与系统回退的职责明确。字体文件分发需单独确认许可，不能直接把系统字体打包进仓库。

### T05｜P1：统一混排基线、行高与中文断行

**位置**：`layout/layout.py` 的 line box/inline formatting；`typography/text.py`。

1. 每行根据参与 run 的 ascent/descent 及 CSS line-height 计算共享基线和行框；处理 leading 分配，不能按每个 face 的行顶再建立不同基线。
2. 以共享基线放置英文、中文和替代字体，垂直对齐属性在行布局中计算；行高与 glyph ink bounds 分开。
3. 实现 white-space、连续空白、软换行及中文标点禁则的最小一致规则；word-break/overflow-wrap 按属性控制，避免中文标点孤立行首或任意拆英文单词。
4. 长文、链接和表格控件使用同一测量/断行模型；行末空白处理和选区长度分开保存。
5. 新建中英混排、不同字号、上标/下标、粗斜体和窄列样本，验证第一行与后续行的基线稳定性。

**验收**：同一行中英文不忽上忽下，行间不相互覆盖，放大字号后文字不会被固定高度裁掉；中文段落与表格文字可读。

### T06｜P1：先做好灰度抗锯齿，再选择小字号策略

**位置**：`typography/rasterize.py` 的 coverage 与混合；`typography/text.py` 渲染配置。

1. 在 T01/T02 完成后，比较现有 2×2、4×4、自适应/面积覆盖；先用 4×4 作为质量诊断选项，测量成本，不承诺采样翻倍就达到浏览器质量。
2. coverage 保存 8bit 或更高精度中间值；字重不应隐式关闭抗锯齿，渲染质量提示也必须覆盖实际命中的缓存路径。
3. 正确组合 coverage 与源 alpha，再执行一致的 src-over；用黑白、浅灰、彩色和半透明背景检查边缘，避免因整数舍入积累产生脏边。
4. 对色彩空间和文字对比度策略做明确配置与对照，不通过任意 gamma 曲线加黑掩盖轮廓或字距错误。
5. 小字号若依赖 hinting 优先评估成熟后端；自研完整 TrueType 字节码解释器应作为独立长期任务，不能以简单强制取整冒充 hinting。

**验收**：12–18px 的圆弧与斜线更平顺、笔画不糊成团；黑底白字与半透明文字不出现明显光晕；相同模式的缓存命中与未命中一致。

### T07｜P1：保留亚像素位置，正确处理 DPI 与缩放

**位置**：`typography/text.py`、字形缓存、布局到绘制的坐标转换、`app/gui.py`。

1. 布局和 pen position 使用浮点 CSS 像素；仅在确定光栅化采样位置时转换到设备坐标，避免每个字独立截断。
2. 把 CSS 尺寸、页面 zoom 和 device scale 明确分开，按最终物理字号生成位图；不把 DPR 与用户缩放重复相乘。
3. 选择可控的亚像素相位桶，例如横向 1/4px，cache key 包含相位；若后端直接支持分数位置，保留其定位信息。
4. GUI 以像素一致的方式呈现渲染结果，避免把已抗锯齿的小字号位图反复缩放；视口/DPI 改变时重新渲染必要字形。
5. 测试 DPR 1/1.25/1.5/2 和 zoom 80%/100%/125%/150%，同时检查编辑光标、命中和裁剪坐标。

**验收**：缩放没有明显字距跳变，跨屏 DPI 改变不会持续模糊；文字、光标与点击位置一致。本次未修改系统缩放设置。

### T08｜P1：字重、斜体、shaping 和符号支持

**位置**：字体匹配、GlyphRun 生成和可选 DirectWrite/HarfBuzz 适配层。

1. 优先使用真实 bold/italic face；合成样式作为明确回退，合成粗体避免过度膨胀导致字腔堵塞，斜体 overhang 计入墨迹边界。
2. 将连字、kerning、组合附标、方向和 cluster 定位接到 shaping 结果；不能只把每个 Unicode 字符独立 cmap 后累加宽度。
3. 渐进验证 AV/To、fi/ffi、带重音字符，再扩展阿拉伯文、印度文字和 bidi；字体和后端不支持的能力明确记录，不以拉丁样本代替复杂文字验收。
4. 彩色 emoji 单独定义字体表支持、回退和 alpha 合成策略；先保证缺字不被错误替换，再实现彩色格式。

**验收**：字重和斜体切换不改变不该改变的行定位，cluster 不被光标或换行错误拆开；shaping 与绘制后端的 glyph ID 命名空间一致。

### T09｜P1：以页面可读性修正 UA 样式和控件

**位置**：`app/browser.py` 的 UA 样式、`style/css.py`、布局与绘制、GUI 编辑层。

1. 审核默认正文、标题、段落、列表、链接和表单的字号、行高、间距；页面未指定时采用合理默认，作者 CSS 正常覆盖。
2. 16px 正文、约 1.4–1.6 行高可作为诊断样本的阅读基线，不作为覆盖所有网站的强制样式；等宽字体只用于代码等相应语义。
3. 让 input/textarea/button 的字体继承、内边距、边框和编辑区域统一，修正控件文字与普通文本使用不同测量模型的问题。
4. 页面错误状态也通过正常文字管线排版；本次百度错误页的拥挤文案需加入回归，不能只美化导航工具栏而保留不可读页面。
5. 检查 inline 背景/边框、下划线、文字颜色、裁剪和滚动后的命中，避免通过扩大字距掩盖位置错误。

**验收**：错误页、简单文章、搜索表单和表格都可读；控件标签没有裁切或上下偏移。此项不以修改网站 HTML 来迁就引擎。

### T10｜P1：缓存与 GPU 只加速正确的 glyph run

**位置**：字形 mask 缓存、显示列表、后续 GPU 后端。关联 [GPU 迁移方案](GPU光栅化迁移方案.md)。

1. cache key 包含稳定 font face/collection index、glyph ID、设备字号、variation/style、DPR/相位、hinting/AA 模式和生成版本；采用按字节预算的 LRU。
2. 分开 shape、metrics、outline、glyph bitmap 和页面 tile 缓存，字体解析/加载完成时使相关层失效。
3. GPU 使用带 bearing/advance 的 R8 coverage atlas 和已定位 GlyphRun；采用一致 alpha 与纹理边界策略，防止双线性采样泄漏到相邻字形。
4. 小字号正文先以高质量灰度 mask 为基准，再研究 SDF/MSDF 的适用字号和误差；不能默认 SDF 会比 hinting 字体更清晰。
5. 测量冷/热缓存、滚动、缩放、字体切换、图集淘汰与设备恢复；比较同一文字的视觉结果，不能仅看帧率。

**验收**：缓存或 CPU/GPU 后端切换不会改变换行、基线和文字内容；热缓存速度改善且内存受控。GPU 迁移不能先于轮廓与定位修复成为“字体变美”的验收证据。

## 5. 推荐交付顺序

| 阶段 | 工作 | 可复核交付 |
|---|---|---|
| 1：修形状 | T01、T02 | 原始 Arial 字样不变形，bearing/descender 正确，缓存与直接绘制一致 |
| 2：修排版 | T03、T04、T05 | 文字测量与绘制一致，字体选择可追踪，中英文混排与行内元素稳定 |
| 3：提观感 | T06、T07、T08 | 小字号、粗斜体、缩放、复杂文字逐项对照；可选成熟后端小范围验证 |
| 4：整页与性能 | T09、T10 | 文章/表单/错误页可读，CPU/GPU 和缓存切换不改变排版 |

第一阶段不需要换 GUI 框架或接 GPU。完成后再截图比较，否则抗锯齿可能只是把错误字形变得更平滑。

## 6. 测试与验收矩阵

| 维度 | 建议样本与检查 |
|---|---|
| 字形几何 | O/B/8/@/%、g/j/p/q/y、空格、重音、复合字形；字腔拓扑、部件边界、bearing、advance |
| 字号/样式 | 12/14/16/18/24/36/48px，400/700，正常/斜体；真实 face 与合成回退分开 |
| 字族/回退 | 固定同一 Arial 做几何基准；再用已记录的中文字体、缺失字体、符号字体测试选择逻辑 |
| 排版 | 中英混排、连续 span/strong/em/a、pre、多空格、窄列、表格、表单、长错误信息 |
| DPI/变换 | DPR 1/1.25/1.5/2，多个 zoom、分数 x/y、负 bearing、边界裁剪、滚动与命中 |
| 合成 | 白/黑/彩色背景、半透明文本、图层透明度与变换，检查脏边和光晕 |
| 缓存 | 冷热缓存、字号/字重/字体切换、字体加载完成、LRU 淘汰、CPU/GPU 一致性 |

先把正确性门槛设为：字符不被误替换、字腔/轮廓正确、基线和测量一致、无非预期裁剪。随后才比较平滑度、对比度和可读性。

同一字体文件、尺寸和 shaping 模式下比较 glyph advance 与偏移；固定后端建立像素 golden。跨系统或与浏览器比较时记录字体哈希、DPR、hinting/AA、视口和版本，分别看结构位置与前景图像差异，不要求不同文字栈像素完全相等。

未来针对行框边界可以先设 1 CSS px 的对照容差作为起点，再按定位误差分布收紧；这只是建议标准，本次没有完成修复后验收，也没有测得观感改善百分比。
