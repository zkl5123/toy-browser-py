# toy-browser-py 浏览器内核全面评估报告

我会按照真实浏览器的工程标准评估你的项目，而不是仅仅检查代码能否运行、已有测试能否通过。

这里需要先明确一个核心区别：能够把 HTML 渲染成像素的程序，不等于能够正确运行现代网页的浏览器。 真实浏览器还需要处理 HTML/CSS/JavaScript 标准兼容性、网络协议、安全隔离、交互行为、页面生命周期、渲染性能和长期稳定性。

从压缩包的初步检查来看，你的项目已经不只是一个简单的 HTML 渲染器。它包含独立的 HTML 解析器、CSS 引擎、布局系统、软件光栅化器、玩具 JavaScript 引擎、HTTP/TLS 网络层、Tkinter 多标签 GUI、字体解析、Cookie、Web API 和增量渲染等模块。

但项目文档中大量使用了“完整化”“真实化”“兼容”等表述。这些表述需要通过独立测试验证，不能直接作为功能已经达到浏览器标准的证据。

## 一、评估原则

实现验证

检查源代码、模块边界、异常处理、资源管理和实际实现，确认功能是否真实存在，而不是只看 README 和路线图。

实测验证

运行项目自带测试，增加边界条件测试，并检查测试是否真正验证了预期行为。

真实浏览器对标

以 Chromium、Firefox、Web Platform Tests（WPT）以及 HTML、CSS、ECMAScript、Fetch 等相关标准为参照，区分基础实现、部分兼容和真正符合标准的功能。

工程与安全审查

检查恶意网页、跨源访问、无限循环、超大资源、网络挂起、状态污染和 GUI 卡顿等真实浏览器必须面对的问题。

有一个重要限制：当前拿到的是源代码压缩包，而不是你正在运行的完整桌面环境。因此，我会区分已经通过源代码或运行测试确认的问题、需要进一步实测的问题以及架构上存在的风险，不会把尚未运行的功能写成已失败，也不会把自测通过等同于浏览器标准兼容。

## 二、总体评估结论

我的初步判断是：这是一个功能覆盖面较广、适合学习浏览器内部机制的 Python 浏览器原型，但目前不能认定为达到真实可用浏览器的标准。

你的优势在于已经把大量浏览器子系统放进同一个工程里，并建立了规模可观的测试集。当前最大的障碍不是继续增加 CSS 属性或 JavaScript 方法，而是标准兼容性的系统性缺口、浏览器安全边界、脚本执行隔离、渲染可靠性，以及独立验证体系。

### 2.2 为什么功能很多，仍然不能算真实浏览器？

从项目文档和测试中已经能看到若干明确的简化行为：

* `@supports` 的测试明确说明：无论条件是否真正支持，都会返回 `True`。

* `@font-face` 已有规则解析测试，但文档注明尚未实现真正的网页字体加载。

* `WebSocket` 会在本地模拟连接和消息，不进行真实网络通信。

* `localStorage` 使用内存存储，刷新或关闭后不能保证持久化。

* CSS Grid 采用等宽列的简化算法，不能等同于完整的 Grid Track Sizing。

* `position: sticky`、动画、滚动、CSP 和 CORS 等功能虽然已有实现或测试，但仍需检查它们是否贯穿完整浏览器流程。

这些并非所有项目都必须立刻实现，而是说明应当把功能明确标为“已支持”“部分支持”“仅解析”“模拟实现”或“尚未实现”，避免功能名称让人误以为已经符合标准。

### 3.1 已确认的字体渲染问题

在当前 Linux 测试环境下，多个测试出现相同异常：

```
AttributeError: 'NoneType' object has no attribute 'ascent'
```

调用链集中在 `text.py` 的 `_face_baseline()` 和 `draw_text()`，涉及的场景包括 CJK 文本绘制、完整渲染管线，以及 GUI 页面加载。

这表明当字体解析或字体回退未能返回有效字体对象时，绘制路径缺少可靠的兜底处理。

需要注意两点：

1. 当前环境报告无法找到可用的 CJK 字体，因此部分失败可能与测试环境有关，不能直接推断在你的 Windows 环境中也会以相同方式失败。

2. 即便根因是环境缺少字体，浏览器也不应因为字体缺失而让整个页面渲染崩溃。正确的行为应当是回退到可用字体，或者使用明确的默认字体完成绘制。

另外，`test.py` 中有一个 `text_measure_consistency` 测试失败，测量值为 `44.4921875`，而测试预期的 TTF 总宽度为 `33.8046875`。这值得单独调查，但目前还不能断定是字体度量算法、字体选择还是测试预期的问题。

### 3.2 测试结果应该如何解读？

现有测试能证明很多局部功能在特定输入下可以工作，但还不能证明：

* HTML、CSS 和 JavaScript 在复杂页面上符合标准；

* 各个模块组合后仍然正确；

* 缺少系统字体、网络中断、超大页面或恶意脚本不会导致崩溃；

* 与 Chromium 或 Firefox 的布局、DOM 状态、网络请求和最终像素结果一致。

真实浏览器工程通常使用独立的标准测试体系。Web Platform Tests（WPT）提供 API 行为测试、渲染对比测试和崩溃测试等不同类型，适合用于建立下一阶段的验证体系。

## 四、最重要的改进方向：先解决阻断级问题

我建议不要继续按 P34、P35 这样的方式不断叠加功能。应该先暂停功能扩展，建立一次系统性的质量整改周期。

P0：安全隔离和脚本执行控制

最高优先级

为 JavaScript 设置执行预算、超时终止、递归深度限制和资源配额；修复跨源安全策略与 Cookie 安全边界；确保恶意页面不能无限占用进程。

P0：修复渲染崩溃和测试不稳定

最高优先级

解决字体对象为空时的异常、文本测量不一致、主测试超时等问题，并在 Windows 和 Linux 上建立可重复的测试环境。

P1：网络、安全策略与资源加载

统一执行导航、重定向、子资源、Cookie、CORS、CSP 和缓存策略，避免只在某个 API 中解析策略，却没有在实际请求流程中强制执行。

P1：建立标准兼容性基线

以 HTML 解析、DOM、CSS 布局、JavaScript 语言语义为单位逐步对标标准测试，而不是把每个新增属性的单个测试通过视为功能完整。

P2：性能与 GUI 工程化

优化整页布局和全图光栅化、避免界面线程执行耗时任务，建立内存、延迟、吞吐量和稳定性基准。

## 五、分模块全面改进建议

### 5.1 HTML 解析与 DOM

涉及文件：`html_pkg/`、`dom.py`、`browser.py`

当前已经有 HTML 字节流解析、编码识别、void 元素处理、部分自动闭合、原始文本处理和表格错误修复。这是合理的起点。

主要问题是 HTML 解析不是简单的标签匹配。标准解析涉及 tokenizer 状态机、树构建 insertion modes、活跃格式化元素列表、模板内容、命名空间以及错误恢复规则。项目文档也承认当前 adoption agency 和 foster parenting 是简化版本。

建议改进：

1. 把 tokenizer 和 tree builder 明确拆分为两个可单独测试的阶段。

2. 优先覆盖 `table`、`select`、`template`、SVG/MathML、嵌套格式化标签和异常闭合标签等复杂场景。

3. 建立 DOM 的节点类型、属性、父子关系和文本节点行为约束。

4. 补齐 `textContent`、`innerHTML`、节点插入删除、属性变化和事件监听等常见 DOM 操作的行为测试。

5. 引入 HTML 解析标准测试子集，与 Chromium 的 DOM 树结果对比。

不要直接尝试实现整个 HTML 标准。 应先确定目标页面范围，再根据真实兼容性测试结果逐步扩展。

### 5.2 CSS 解析、层叠与布局

涉及文件：`css.py`、`layout.py`、`paint_engine.py`

这是整个项目中最容易产生“功能看起来支持，实际页面却不一样”的部分。

目前已有 flex、grid、position、margin 折叠、浮动、伪类、动画、渐变、裁剪和部分文本布局。问题在于 CSS 的功能正确性通常依赖其他模块的共同语义，而不是单独解析一个属性。

| 子系统      | 主要风险                            | 改进重点                              |
| -------- | ------------------------------- | --------------------------------- |
| CSS 解析器  | 复杂函数、嵌套规则和转义字符可能处理不完整           | 建立词法与语法测试，正确处理字符串、括号和嵌套结构         |
| 层叠与继承    | `!important`、继承、初始值和自定义属性可能互相影响 | 按标准建立独立的计算样式阶段                    |
| Flexbox  | 多行布局、最小尺寸、基线、自动边距和尺寸分配的边界行为     | 使用标准布局测试，不只测简单居中与分配               |
| Grid     | 等宽列算法不能替代完整轨道尺寸计算               | 逐步实现 `minmax()`、自动轨道、显式/隐式网格和跨列项目 |
| Position | `sticky`、包含块、层叠上下文与滚动容器存在耦合     | 统一定义包含块、绘制顺序和裁剪规则                 |
| 文本布局     | 字体度量、行盒、换行、双向文本和字体回退            | 把字体度量与行布局拆开验证                     |

特别需要关注 `paint_engine.py` 中的 z-index 排序。简单地按 `z-index` 排序绘制命令，并不能自动实现完整的 CSS stacking context 语义。嵌套透明元素、定位元素、变换和裁剪可能改变绘制顺序。

另一个明确的改进点是 `@supports`：现有测试将其描述为始终返回 `True`。这应该改为基于真实属性和值支持情况进行判断；不支持的声明不能被当作已经支持。

### 5.3 JavaScript 引擎

涉及文件：`js.py`

这是我最不建议继续以“增加语法数量”方式开发的模块。

你的引擎已经有词法分析、Pratt 解析、解释执行、作用域、TDZ、类、箭头函数、数组方法、Promise 玩具实现和一些内置对象。但这些功能不能简单相加后就变成兼容现代网页的 JavaScript 引擎。

重点问题如下。

第一，缺少执行预算。

源码中 `while` 和 `for` 的执行路径使用循环解释执行。当前可见实现没有统一的指令预算或执行截止时间机制。

例如恶意页面中的无限循环可能占用执行线程，使页面加载卡住。单纯在 GUI 外面加一个计时器并不能停止正在执行的 Python 解释器代码。

建议在解释器核心增加：

* 每个脚本的最大执行步数；

* 递归和调用栈深度限制；

* 可协作检查的取消标记；

* 对数组长度、字符串长度、对象数量等设置合理上限；

* 将运行时异常和资源耗尽作为独立错误类型处理。

如果以后希望运行不可信网页，应考虑把脚本执行放入独立进程，并设置操作系统层面的资源限制。

第二，语言语义不完整。

JavaScript 的标准语义远不止常见语法。需要重点检查：

* 原型链与属性描述符；

* `this`、闭包、函数调用规则；

* 异常传播和严格模式；

* 数字类型、`NaN`、`Infinity`、类型转换；

* `Map`、`Set`、迭代器和生成器；

* Promise 微任务、任务队列与事件循环；

* 模块加载、动态导入及异步语义。

这些能力存在相互依赖关系。逐个增加语法而不建立语义层，后续会导致大量兼容性补丁。

第三，通用 `getattr` 回退值得重点审计。

在解释器中，使用 Python 的 `getattr()` 作为通用对象属性和方法分派的后备路径，会使 JavaScript 对象行为与 Python 对象行为发生耦合。

建议改为显式的 JavaScript 值模型和属性访问协议，明确区分 JS 对象、数组、函数、DOM 节点和宿主对象。这样才能控制对象可见性、方法调用、异常转换和访问权限。

我的建议： 如果目标是浏览器兼容性而非研究解释器本身，优先评估集成成熟的 JavaScript 引擎的可行性。如果坚持纯标准库和自研引擎，则应把产品目标限定为受支持的网页子集，不应承诺完整现代 JavaScript 兼容。

### 5.4 网络层、Cookie、CORS 与 CSP

涉及文件：`net.py`、`cookie_store.py`、`browser.py`、`gui.py`

网络层已经具备 HTTP/TLS、重定向、gzip、缓存、连接池和并发子资源拉取等功能。它们是有价值的基础，但真实浏览器的网络行为需要更多安全约束。

#### 必须优先修复的点

1. Cookie 安全边界

`cookie_store.py` 的文档明确表示尚未执行完整的 SameSite、Secure、HttpOnly 安全约束。域名匹配、路径匹配、过期时间和属性校验都需要加强。

建议先实现安全的 Cookie 属性模型、域名规则和请求上下文，再处理 SameSite、HttpOnly、Secure 与持久化。

2. CORS / CSP 必须实际拦截

当前 `net.py` 提供策略解析和判断函数，但仅有这些 API 不代表实际加载流程已经执行了完整的策略控制。

需要从真实调用链确认：脚本执行、样式表、字体、图片、iframe、fetch 和重定向是否都在正确阶段执行策略检查。

3. 资源大小限制

网络响应通过 `resp.read()` 读取完整响应体。需要确认整个 HTTP 读取路径是否对压缩前后大小、读取时间和内存消耗设置上限。

不可信服务器返回超大内容或高压缩比内容时，应有明确的资源预算，不能只依赖字体文件限制或 Python 进程总内存保护。

4. 重定向与本地网络访问

URL 解析、重定向和子资源加载应统一检查目标地址。若浏览器未来用于自动打开不可信网页，需要考虑私有 IP、回环地址、特殊地址格式和 DNS 解析变化等风险，避免页面通过重定向或子资源请求访问非预期服务。

跨源隔离并不是简单地检查两个字符串是否相同，而是基于 scheme、host、port 等组成的 origin，并且要根据资源类型和请求模式决定是否允许读取响应。

### 5.5 字体与图形渲染

涉及文件：`text.py`、`font.py`、`ttf_font.py`、`rasterize.py`、`paint.py`、`paint_engine.py`

你已经投入大量工作实现字体表解析、字形轮廓、CJK 回退、字形缓存和软件光栅化。但字体渲染仍应当从“功能演示”升级为“输入异常也能稳定渲染”。

建议按以下顺序处理：

1. 统一字体加载的返回契约：成功返回有效字体对象，失败返回明确错误或可用回退对象，不允许下游接收到未处理的 `None`。

2. 将字体选择、度量、字形轮廓生成和像素绘制分离。

3. 建立字体缺失、损坏文件、缺字、粗体回退和 CJK 混排的测试。

4. 对比同一字体下的文本宽度、基线、行高和换行位置。

5. 对字形缓存、轮廓缓存和内存上限进行压力测试。

6. 对每个绘制命令建立可重放的最小测试用例，避免整页测试才能发现故障。

特别要检查 `mem_guard.py`：`tracemalloc` 监控的是 Python 跟踪分配的内存，并不能作为整个进程所有内存消耗的硬性保证。6 GB 的配置值不能直接证明进程一定会在达到 6 GB 时安全停止。

### 5.6 GUI 与页面交互

涉及文件：`gui.py`、`browser.py`

当前 GUI 的一个明显设计风险是页面加载和渲染路径中存在同步操作。

项目文档说明，页面滚动通过测量文档高度、生成完整页面位图，再按滚动偏移裁剪显示；完整内容高度还被限制在 16,000 像素。这种方式适合早期实现，但对长页面、复杂布局和大图会产生明显的内存和响应延迟压力。

建议：

* 把网络加载、HTML 解析、布局和光栅化放到受控的后台任务中，Tkinter 控件更新仍在 GUI 主线程执行。

* 为每次导航建立唯一任务标识，取消旧导航的待处理工作，避免旧页面的迟到结果覆盖新页面。

* 将完整页面位图方案改为分块绘制或可视区域优先渲染。

* 对输入框、按钮、键盘焦点、表单、链接点击和滚动统一建立事件派发层。

* 明确前进/后退、重载、页面加载失败、标签关闭时的状态清理规则。

* 将页面布局、绘制和导航状态解耦，避免每次交互都需要重新构建整个页面。

建议先以“长页面滚动不卡顿、网络挂起不冻结 GUI、连续导航不串页”为三个可测量的工程目标。

## 六、架构层面的调整建议

现有模块数量不少，暂时不需要推倒重写。但应建立稳定的内部接口，避免新功能继续扩大各模块之间的耦合。

浏览器外壳

Tab / Navigation / History / User Input

导航与资源管理

URL / HTTP / Redirect / Cache / Cookie / Security Policy

文档与脚本

HTML Parser / DOM / CSSOM / JavaScript / Web APIs / Events

渲染管线

Style → Layout → Display List → Rasterization → Compositing

输出与交互

Bitmap / GUI / Scroll / Hit Testing / Accessibility

这张图是建议的逻辑架构，不代表现有项目已经完整实现所有层。

尤其建议新增三个明确的基础设施：

* 任务调度器： 管理导航、资源加载、脚本执行和渲染任务的取消、优先级与资源配额。

* 安全策略执行层： 统一处理 origin、CORS、CSP、Cookie 和网络访问边界。

* 标准兼容性测试层： 将外部标准测试、项目回归测试、性能测试和崩溃测试分开管理。

同时，建议为 DOM、CSS、JavaScript 和渲染模块建立稳定的输入输出接口。增量布局应以明确的 dirty 标记、依赖关系和失效范围为基础，避免局部缓存失效后继续使用旧的计算结果。

## 七、如何建立真正有效的浏览器测试体系

目前你的测试主要是项目自己编写的 Python 测试。这对于开发非常重要，但还缺少独立的对照标准。

建议分四层建设。

1. 第一层：单元测试

   每个模块独立验证解析、计算和异常处理，例如 CSS specificity、URL 解析、Cookie 规则和 JS 类型转换。

2. 第二层：端到端测试

   从 HTML 输入开始，验证 DOM、计算样式、布局盒、绘制命令和最终像素。不能只断言某个属性已经存入对象。

3. 第三层：差分测试

   使用相同的 HTML、CSS、JS 和视口尺寸，在 toy-browser-py 与 Chromium 中执行，对比 DOM 状态、布局位置、文本换行、事件结果和截图。对于字体与抗锯齿差异，应设定适当的容差。

4. 第四层：标准与压力测试

   按目标范围引入 WPT、ECMAScript Test262 的适用子集，以及长页面、恶意脚本、超大响应、断网、重定向循环和多标签压力测试。

WPT 官方文档明确区分 API 测试、渲染参考测试、视觉测试和崩溃测试。这种分层非常适合你的项目，能避免所有问题都依赖一个庞大的 `test.py`。

![](https://www.google.com/s2/favicons?domain=https://web-platform-tests.org\&sz=32)

web-platform-tests documentation

+1

还建议把测试报告分成以下指标：

| 指标       | 用途          |
| -------- | ----------- |
| 标准测试通过率  | 判断目标功能的兼容程度 |
| 回归测试通过率  | 防止修复导致旧功能退化 |
| 崩溃率      | 衡量页面稳定性     |
| 首屏渲染耗时   | 衡量用户打开页面的体验 |
| 长页面滚动延迟  | 衡量布局与绘制性能   |
| 峰值内存     | 衡量资源治理能力    |
| 恶意脚本终止时间 | 衡量执行隔离与取消机制 |

只有在测试范围、运行环境和通过率都可重复的前提下，这些指标才有可比性。

## 八、建议采用的三阶段改进路线

## 阶段一：稳定性与安全基线

立即开始

目标：停止崩溃、挂起和明显的安全边界失效

* 修复字体回退导致的 `NoneType` 异常。

* 调查文本度量测试失败。

* 为 JS 解释器增加执行预算和取消机制。

* 审计 Cookie、CORS、CSP、重定向与子资源加载。

* 拆分主测试脚本，设置明确的测试超时和失败报告。

* 在 Windows 与 Linux 上建立固定版本的测试环境。

## 阶段二：标准兼容性建设

第二优先级

目标：让已支持功能在边界条件下也正确

* 建立 HTML、CSS、JS、DOM、网络和字体的能力清单。

* 从 WPT 和 Test262 中选取与你的目标范围匹配的测试子集。

* 用 Chromium 做 DOM、布局、事件和截图差分。

* 修复 flex/grid、定位、层叠、文本布局等系统性差异。

* 对未实现功能明确降级策略，不再让模拟 API 冒充真实实现。

## 阶段三：性能与产品化

第三优先级

目标：从可运行的研究项目变成稳定的桌面工具

* 引入后台任务、导航取消和可视区域优先渲染。

* 完善表单、焦点、键盘、滚动和历史导航。

* 评估集成成熟 JS 引擎的成本与收益。

* 优化缓存策略、增量布局、字体缓存和图像解码。

* 清理测试产物、`__pycache__` 和不必要的大型输出文件。

* 建立持续集成和每次提交自动回归机制。

## 九、项目管理与代码维护建议

压缩包中还有一些值得整理的工程细节：

1. `test.py` 已经非常庞大，建议按 HTML、CSS、JS、网络、字体、GUI 等模块拆分测试入口，保留统一的总测试命令。

2. 路线图中已完成的里程碑应有明确的验收标准，不能仅凭实现了某个方法或属性就标记完成。

3. `out_event.ppm` 等大型渲染产物和 `__pycache__` 不适合默认进入源码发布包。

4. 应增加依赖与运行环境说明、固定的 CI 测试命令，以及可复现的性能测试输入。

5. 文档应区分“已实现”“已验证”“部分支持”和“模拟实现”，并为每个功能记录测试证据。

## 十、最终建议

如果你的目标是做一个可展示、可学习、可逐步完善的 Python 浏览器，那么现有项目基础值得继续保留，不必推倒重写。重点应放在稳定性、模块接口、标准子集和测试体系。

如果你的目标是像 Chrome、Edge 或 Firefox 一样打开现代网站，支持真实登录、复杂前端应用和常见 Web API，那么仅靠当前的纯 Python 自研内核继续增加功能，成本会快速上升。尤其是完整 JavaScript 引擎、现代 CSS 布局、浏览器安全隔离和网页兼容性，都是需要长期投入的系统工程。

我最推荐的下一步是：

先完成一次 P0 专项整改：字体渲染崩溃、JS 执行预算、网络与 Cookie 安全边界、完整测试报告。 这几项解决后，再建立与 Chromium 的差分测试和 WPT 兼容性基线。这样后续每一项功能改进都能用实际数据证明有效，而不是继续依赖路线图上的功能数量。

本次已经完成了源码初检、语法编译和多组测试执行，但尚未完成完整主测试套件、Windows 原生 GUI 实测、与 Chromium 的截图差分以及完整安全渗透测试。因此，这份报告是有实际执行证据支撑的第一轮工程审查，不是已经通过全部浏览器标准认证的结论。
